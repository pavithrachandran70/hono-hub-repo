**Ticket:** PER-105  
**Title:** Release the discarded response body when middleware replaces `c.res`  
**Type:** Epic  
**Created:** 2025-01-22

---

## Overview

Implement automatic cleanup of discarded response bodies when middleware replaces `c.res`, preventing stream leaks and unbounded buffering of cloned body branches. The cleanup mechanism is internal to the `Context` class and triggers automatically on `c.res` assignment without requiring changes to middleware code or public APIs.

This epic covers the implementation of the core cleanup mechanism, regression tests for affected middleware (ETag, PrettyJSON), verification of other middleware, and a comprehensive test suite ensuring the cleanup contract works correctly across all scenarios and runtimes.

## Schema / API Contracts

### Internal: `Context.res` setter contract

**Before:**
```typescript
set res(res: Response) {
  this._res = res
}
```

**After:**
```typescript
set res(res: Response) {
  // Cleanup previous body if replacing with a different body
  if (this._res && this._res.body !== res.body && this._res.body) {
    try {
      this._res.body.cancel()
    } catch (e) {
      // Development: log error for debugging
      // Production: silently ignore
      if (process.env.NODE_ENV === 'development') {
        console.error('Failed to cancel previous response body:', e)
      }
    }
  }
  this._res = res
}
```

**Contract guarantees:**
- Previous response body is cancelled when `c.res` is replaced
- Reused bodies (same reference) skip cancellation
- Cleanup errors do not propagate or prevent the new response from being assigned
- Header merging behavior (including `set-cookie`) is unchanged

**Affected middleware:**
- ETag middleware (returns 304, computes ETag from body)
- PrettyJSON middleware (formats JSON, clones body)
- Cache middleware (cache hits replace response)
- Compress middleware (compression replaces response)
- Timeout middleware (timeout replaces response)
- JSX-renderer middleware (SSR replaces response)
- Secure-headers middleware (header injection replaces response)

**Note:** Middleware paths (`src/middleware/etag/`, `src/middleware/pretty-json/`, `src/middleware/cache/`, etc.) are assumed to exist based on ticket references but are not confirmed in the provided repo-tree (which cuts off at `src/helper/cookie/index.ts`). These paths must be verified before implementation.

No changes to middleware code required — cleanup is automatic.

## Risks

### High: Multi-runtime ReadableStream API variance

**Risk:** `ReadableStream.cancel()` behavior may differ across Bun, Deno, Node.js, and Cloudflare Workers. Some runtimes may not support `cancel()` on all stream types or may throw non-standard errors.

**Mitigation:**
- Wrap `body.cancel()` in try/catch with error suppression (production) or logging (development)
- Test on all supported runtimes (Bun, Deno, Node.js, Cloudflare Workers) to verify `cancel()` behavior
- Accept that cleanup is best-effort — if a runtime does not support `cancel()`, the cleanup is skipped silently

**Residual risk:** Stream leaks may persist in runtimes with incomplete `ReadableStream.cancel()` support, but this is no worse than the current behavior (no cleanup at all).

---

### Medium: Body reference equality may not catch all reuse patterns

**Risk:** Middleware may construct a new `Response` object with the same underlying stream but a different `body` object reference (e.g. wrapping the stream in a new `ReadableStream` instance). The reference equality check (`previousBody === newBody`) would fail, triggering cancellation of a body still in use.

**Mitigation:**
- Document the expectation that reusing a body means passing the same `body` reference to the new `Response`
- Test the concrete reuse patterns in Hono middleware (verify that `new Response(previousResponse.body, ...)` preserves the reference)
- If false positives occur, consider tracking stream identity via a WeakMap or other mechanism (deferred to future work)

**Residual risk:** False positives (cancelling a reused body) would break the response. This requires careful testing of reuse patterns in ETag, cache, and other middleware.

---

### Medium: Existing tests may break if they rely on uncancelled streams

**Risk:** Existing test cases may assert on stream state after `c.res` replacement, expecting the old body to remain open. The new cleanup behavior would break these tests.

**Mitigation:**
- Run full test suite (`pnpm test`) after implementing cleanup to identify broken tests
- Update test assertions to expect cancelled streams (or rewrite tests to avoid the assumption)
- Review test coverage for middleware that replace `c.res` and ensure tests align with the new cleanup contract

**Residual risk:** Test churn. This is acceptable as long as the new behavior is correct and the tests are updated accordingly.

---

### Low: Header merging regression

**Risk:** Modifying the `res` setter could inadvertently break header merging logic (especially `set-cookie` append behavior).

**Mitigation:**
- Preserve the existing `this._res = res` assignment logic exactly as-is (cleanup happens before assignment, not in place of it)
- Add a regression test case in `src/context.test.ts` to verify `set-cookie` headers are appended (not overwritten) when `c.res` is replaced
- Run existing header-related test cases to confirm no regression

**Residual risk:** Minimal. The cleanup logic is isolated from header merging, and the assignment itself is unchanged.

---

### Low: Performance impact of try/catch in hot path

**Risk:** Adding a try/catch block to the `res` setter could introduce measurable overhead in high-throughput scenarios (e.g. Cloudflare Workers handling thousands of requests per second).

**Mitigation:**
- Benchmark the `res` setter before and after the change on a representative workload
- If overhead is measurable and unacceptable, consider moving the cleanup to a conditional branch that only runs when the previous body exists (avoiding the try/catch when no cleanup is needed)
- Profile on Cloudflare Workers specifically, as it is a performance-sensitive runtime

**Residual risk:** Acceptable. The try/catch overhead is likely negligible compared to the cost of body cloning and stream I/O. If it becomes a problem, the fix is straightforward (conditional cleanup).
